# معمارية Extreme IP Guard

## الرؤية

Extreme IP Guard ليس نسخة تقليدية من أدوات مراقبة الأجهزة، بل منصة دفاع
مؤسسية حديثة تجمع بين:

- **Zero Trust Endpoint**: لا يتم الوثوق بالجهاز لمجرد أنه داخل الشبكة.
- **Risk-Adaptive Control**: القرار يتغير حسب خطورة الجهاز وسياق البيانات.
- **Data Loss Prevention**: منع تسرب البيانات الحساسة عبر القنوات عالية
  المخاطر.
- **Security Operations**: تحويل الأحداث إلى إجراءات قابلة للتدقيق والاستجابة.
- **Privacy by Design**: شفافية، صلاحيات دقيقة، احتفاظ محدود، وسجلات تدقيق.

## الحدود الأخلاقية والأمنية

النظام مصمم للدفاع والإدارة الشرعية فقط. يجب ألا يتحول إلى أداة تجسس خفية أو
جمع كلمات مرور أو تسجيل مفاتيح أو تجاوز صلاحيات. أي نشر حقيقي يتطلب إشعار
الموظفين، موافقة قانونية، سياسات احتفاظ، وضوابط وصول صارمة.

## المكونات

### 1. Control Plane

الخادم المركزي الذي يدير الأصول، السياسات، الأحداث، التقارير، والتكاملات.
في النموذج الأولي يمثله:

- `app.py`
- `eipg/server.py`
- `eipg/storage.py`

في الإنتاج يجب أن يتحول إلى خدمة API خلف بوابة آمنة مع SSO/MFA وRBAC.

### 2. Endpoint Agent

وكيل ظاهر ومصرح به على أجهزة المؤسسة. دوره إرسال حالة الجهاز وأحداث DLP
المسموح بجمعها. في النموذج الأولي يمثله:

- `endpoint_agent.py`

في الإنتاج يجب توقيع الوكيل، تسجيله بشهادة، تشغيله بصلاحيات محدودة، ومنع أي
جمع زائد عن الحاجة.

### 3. Risk Engine

محرك تقييم المخاطر يحسب درجة من 0 إلى 100 بناءً على:

- حالة التشفير.
- وجود EDR.
- حالة الجدار الناري.
- عمر تحديثات النظام.
- الثغرات الحرجة والعالية.
- محاولات الدخول الفاشلة.
- أحداث DLP الأخيرة.
- التعرض الخارجي.
- وجود بيانات حساسة على القرص.
- حجم الخروج الشبكي غير المعتاد.

الناتج:

| الدرجة | المستوى | الإجراء |
| --- | --- | --- |
| 0-34 | Low | Allow |
| 35-59 | Medium | Monitor |
| 60-79 | High | Restrict |
| 80-100 | Critical | Isolate |

### 4. DLP Decision Engine

محرك قرار لحركة البيانات:

- Public: السماح.
- Internal: مراقبة أو طلب موافقة عند القنوات عالية المخاطر.
- Confidential: منع أو عزل عند الوجهات غير الموثوقة، أو طلب موافقة إذا كانت
  مشفرة.
- Secret: منع الخروج إلى أي وجهة غير موثوقة وطلب موافقة حتى للوجهات الموثوقة.

القنوات التي يمكن نمذجتها:

- البريد الشخصي.
- التخزين السحابي الخارجي.
- وسائط USB.
- Clipboard.
- تحميلات الويب.
- الطباعة أو المشاركة الداخلية في مراحل لاحقة.

### 5. Response Orchestrator

الطبقة التي تربط قرارات المنصة بأدوات فعلية:

- EDR لعزل الجهاز.
- NAC لتغيير VLAN أو سياسة الوصول.
- SASE/CASB لمنع الوجهات السحابية.
- SIEM لإرسال الأحداث.
- SOAR لتشغيل playbooks.
- ITSM لفتح تذاكر علاج.

النموذج الأولي يوفر API لعزل أو استعادة حالة الأصل بشكل محاكى.

### 6. Governance Layer

حوكمة المنصة ليست ميزة جانبية، بل جزء أساسي:

- RBAC حسب الدور.
- موافقات متعددة للقرارات الحساسة.
- Audit Log غير قابل للتلاعب.
- إخفاء بيانات شخصية عند العرض.
- Retention حسب نوع الحدث.
- Export قانوني مضبوط.

## نموذج البيانات

### Asset

يمثل جهازاً أو خادماً:

- asset_id
- hostname
- owner
- department
- ip_address
- os_name
- status
- risk_score
- risk_level
- policy_action
- posture
- metadata

### DLP Event

يمثل محاولة حركة بيانات:

- asset_id
- username
- channel
- sensitivity
- destination
- destination_trusted
- bytes_count
- encrypted
- action
- severity
- reason

### Audit Log

يسجل القرارات والأفعال:

- actor
- action
- target_type
- target_id
- details
- created_at

## مبادئ الإنتاج

1. **Signed Enrollment**: لا يقبل الخادم وكيلاً غير مسجل وموقع.
2. **Mutual TLS**: اتصال الوكلاء والخادم بشهادات متبادلة.
3. **Policy Versioning**: كل قرار مرتبط بإصدار السياسة.
4. **Least Privilege**: أقل صلاحيات ممكنة لكل خدمة.
5. **Explainability**: كل قرار له أسباب واضحة.
6. **Human-in-the-loop**: الموافقة البشرية عند القرارات ذات الأثر العالي.
7. **Fail Safe**: عند فشل الاتصال لا يتم تعطيل الأعمال إلا للسياسات الحرجة
   والمحددة مسبقاً.
8. **Privacy Budget**: جمع الحد الأدنى من البيانات اللازمة للدفاع.
